## 帮助 Stumpless 持续改进

Stumpless 致力于在保持尽可能小巧的同时，可靠地完成明确而专注的目标。如果您
发现项目存在问题、希望提出新的功能建议，或希望了解如何参与贡献，请阅读以下
指南以开始参与。同时，无论以何种方式参与项目，请务必遵守
[行为守则](行为守则.md)。


### **熟悉项目的贡献者**

如果您是本库的常规用户，并且对项目已有较深入的了解，可以通过帮助其他用户
解答问题来回馈社区。欢迎前往项目的
[gitter](https://gitter.im/stumpless/community) 聊天室；如遇到您能够解答
的问题，请积极参与讨论。


### **报告问题**

如果您发现项目存在问题，请在提交 issue 之前确认已经完成以下事项：

 * 阅读相关文档，确认该行为并非预期行为
 * 搜索项目中已有的 issue，确认该问题尚未被记录
 * 基于最新版本分支复现该问题

如果完成以上步骤后问题仍然存在，请使用项目提供的 issue 模板，在
[GitHub 项目](https://github.com/goatshriek/stumpless) 中提交 issue，并完整
填写模板所需信息。

如果您已经了解修复方法，也欢迎直接使用项目提供的模板提交 pull request，并
在其中提及对应的 issue 编号。


### **提交贡献**

如果您已经完成了一些修改并希望提交给项目，请创建 pull request。项目团队会
对其进行审查，并评估是否可以合入最新版本。提交贡献时请遵循以下指南：

 * 如果您处理的是相对较小的改动，则无需担心分支中的提交数量，因为这些提交
   在合并到 `latest` 分支之前会被压缩合并为一个提交（squash）。例如，如果
   您正在处理标记为 `good first issue` 的任务，无需刻意整理提交历史，只需
   专注于完成改动即可。为了确保贡献记录能够体现在提交历史和 GitHub 中，您
   仍会被保留为该提交的作者。
 * 如果您处理的是较大规模的改动，将所有内容压缩合并为单个提交可能并不合适，
   因而提交数量和提交组织会更加重要。在这种情况下，请尽量确保每个提交都
   具有清晰的逻辑和独立的价值。如果您需要了解如何调整提交历史，可以参考
   Git Book 中的
   [这一章](https://git-scm.com/book/en/v2/Git-Tools-Rewriting-History)，
   其中介绍了几种常见做法。请注意，这类情况并不常见；如果您不确定自己的
   改动是否属于这种情况，建议先与项目团队确认，再投入复杂且耗时的 rebase
   流程。
 * 如果某个提交解决了或关联到特定 issue，请在提交正文中包含对应引用。


### **提出功能建议**

如果您认为某项新功能值得加入项目，请使用 “Feature Request” 模板在 GitHub
项目中创建 issue。如果该建议适合本项目，您可以在自己的 fork 中开始开发，并
提交 pull request，方便项目团队跟进进展，并在完成后进行合并。如果您暂时没有
时间实现，项目团队会根据优先级将其加入项目
[路线图](../../../docs/roadmap.md)，并在后续安排实现。


### **不接受的贡献类型**

项目团队感谢任何愿意参与贡献的人。不过，为了合理利用项目维护者和贡献者的
时间，有些类型的贡献不会被接受。潜在贡献者应查看以下列表，并避免提交这些
类型的 pull request：

 * 对明显拼写错误和语法问题的修正，可能会根据问题严重程度逐案接受。如果
   此类修改覆盖多处内容，被接受的可能性会更高。换言之，如果您希望进行校对
   类贡献，请完整校对一份或多份文档，而不是只修复单个问题。项目团队强烈
   建议您优先考虑其他形式的贡献。
 * 对大小写、标点或其他风格选择的修改不会被接受。


### **从何处开始**

如果您希望参与贡献，但尚不确定从何处开始，可以先浏览 issue 列表，查找自己
能够处理的任务。特别是带有 `help wanted` 和 `good first issue` 标签的
issue：前者表示项目需要帮助，后者表示任务相对简单。标记为
`good first issue` 的任务通常不具有紧迫时限；如果实际耗时超过预期，请定期
同步进展即可。

[开发说明](../../../docs/development.md) 中包含面向新贡献者的入门内容，建议
阅读。


#### 仍然不确定如何开始

如果您刚开始参与开源社区，并希望获得更详细的贡献流程说明，本节可以帮助您
开始。

Stumpless 的默认分支名为 `latest`，所有新功能分支都基于该分支创建。当下一
版本计划中的所有改动都已实现后，项目会在相应提交上添加以语义化版本号命名
的标签，并更新 `release` 分支，使其指向该提交。因此，`latest` 始终包含最新
改动，而 `release` 始终指向最近一次完整发布版本。

如需创建自己的功能或更新，请先 fork 仓库，并基于 `latest` 分支创建新分支。
请不要忘记在 ChangeLog 中记录您的改动；准备完成后，请创建一个指向 `latest`
分支的 pull request。

在少数情况下，您的工作可能更适合基于 `release` 分支，而不是 `latest` 分支。
不过，这通常比基于 `latest` 开发复杂得多，因为相关改动仍需合并回 `latest`，
而两个分支之间可能已经产生足以导致冲突的差异。此外，这通常还需要发布新的
补丁版本。因此，除非确有必要，否则不建议这样做。确有必要的情况包括：

 * 需要将补丁应用到最近一次发布版本，以修复已损坏的功能
 * 需要对文档进行关键更新，否则可能导致严重误用或破坏性后果

请务必查看[依赖项](../../../docs/dependencies.md)列表，确认您的开发环境具备
所有必要工具。尤其是在进行较大改动之前，请确保能够运行测试和开发工具，以便
在开发过程中持续验证改动。

传统 Git 工作流的详细教程超出了本文档范围，不过以下指南可作为入门参考：

 * [GitHub Guides](https://guides.github.com/introduction/flow/)
 * [Creating a Pull Request from a Fork](https://help.github.com/en/github/collaborating-with-issues-and-pull-requests/creating-a-pull-request-from-a-fork)

概括而言，基本步骤是：fork 仓库，基于 `latest` 创建新分支（在特定情况下也
可能基于 `release`），完成改动并提交，然后创建一个指向主仓库的 pull
request。


### 保持沟通

项目团队会尽量及时响应，通常会在几天内回复新的 issue 和 pull request。在
issue 中请求澄清，或在 pull request 中请求修改，都是常见流程；在内容被
接受之前，通常需要经过若干轮沟通。

有时讨论可能会停滞，导致无法继续推进。如果项目团队正在等待回复，而某个事项
长期没有进展，它最终会因 stale 而被关闭。两个月没有回应的事项会被标记为
stale，并在讨论中发布提醒。如果再过一个月仍没有回应，该事项将被关闭为
stale。

被标记为 stale 的事项仍然可以重新打开，因此事项被关闭并不表示讨论永久结束。
项目团队这样做是为了保持活跃工作的清晰和整洁，使社区成员能够快速了解当前
正在进行和暂未进行的工作。


## 关于 AI 的说明

本项目主要依据质量评估贡献。您可以使用包括 LLM 或其他生成式 AI 在内的任何
工具，前提是您对生成结果拥有足够的控制权和贡献权利，能够将其自由贡献给
项目。

但是，如果您使用 AI 生成低质量的 pull request、issue 或讨论回复，该内容将
被视为与人工提交的低质量内容无异。也就是说，维护者可能会按照行为守则中的
[处理方针](行为守则.md#处理方针)采取相应措施。请尊重所有参与者的时间，在
提交之前认真审查自己的工作和交流内容，通常即可避免此类问题。
